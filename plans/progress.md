## Next task: conjugation engine, Forms tab and deinflection

Spec: §6 (engine and Forms tab) and §2 (deinflection, ranking, result label). Code layout: `architecture.md`. Build in this order. Parts 1 and 2 fit in one session. Part 3 may need its own.

### 1. Conjugation engine

- Pure Kotlin with no Android dependencies, in its own package (e.g. `conjugation/`), so JVM unit tests cover all of it.
- Input: a dictionary form (the spelling to conjugate) and a JMdict POS code. Output: the §6 rows, each with its affirmative and negative forms. A cell can hold several forms (引かないで, 引かなくて) or none (—).
- Covers every class in §6:
  - `v1`;
  - `v5u` `v5k` `v5g` `v5s` `v5t` `v5n` `v5b` `v5m` `v5r`;
  - the godan exceptions `v5k-s` (行く), `v5r-i` (ある), `v5aru` (くださる), `v5u-s` (問う);
  - `vk` (来る, in kanji and in kana);
  - `vs-i` and `vs-s` (する and 〜する verbs);
  - `vs` nouns, conjugated as noun + する;
  - `adj-i`, and `adj-ix` (いい/良い → よくない).
- Unit tests:
  - the two full tables in §6 (引く, 高い), checked cell by cell;
  - for each other class, a representative word checked on its distinctive cells (食べる, 書く/泳ぐ/話す/待つ/死ぬ/遊ぶ/読む/帰る/買う, 行く, ある, くださる, 問う, 来る/くる, する, 勉強, いい/良い).
- The same rule data must be able to run in reverse for part 3. Write the rules as suffix replacements per class (stem ending + inflection suffix), not as code that only works in one direction.

### 2. Forms tab

- Replaces the "coming soon" placeholder. It's shown when the entry has a POS the engine handles (`EntryState.tabs` already uses this condition).
- Title: the conjugation class's Japanese label from `tags.label_ja` (e.g. 五段動詞（く）, 一段動詞, サ変動詞).
- Forms are spelled with the headword (`EntryState.headword`): 掛けた, not かけた. A headword that's a reading (`uk` words) gives kana forms.
- Table layout: row labels in English, then Affirmative and Negative columns. Long forms wrap within their cell. No pitch accent and no glosses.
- If the entry's senses have more than one conjugating POS (e.g. a verb that is both `v5r` and `v1`), show one table per class, each under its own title.
- Check on the device with screenshots: a godan, an ichidan, 来る, a する noun, an い-adjective and いい.

### 3. Deinflection search

- **Candidate generation** (pure Kotlin, unit-tested): run the engine's suffix rules in reverse on the query. The result is a list of (dictionary form, POS class, inflection chain) candidates, and they can chain: 食べられない → 食べられる (negative) → 食べる (potential or passive).
- **Lookup:** look up each candidate's dictionary form as an exact `jp_keys` key (kind 0). Keep an entry only if its `entries.pos` contains the candidate's POS class. Drop a candidate identical to the query itself.
- **Ranking:** deinflected matches are tier 3, below exact and whole-word fuzzy matches and above prefix matches (§2). They're ordered within the tier like the other tiers (common, then frequency). Add a `DEINFLECTED` value to `Tier` in `search/Search.kt`.
- **Matched form:** the written form or reading that matched the dictionary form, highlighted in full. It's carried into the entry page like any other match.
- **Result label:** a deinflected row shows the inflections it undid, in English, using the Forms tab row names, outermost last (e.g. "past, negative" for 引かなかった). If the form is ambiguous, list the readings joined with " or " (食べられる → "potential or passive").
- **Unit tests:** the §2 examples (掛けた → 掛ける, 引かなかった → 引く, 食べられない → 食べる), plus each class's past and negative forms. Also check that the reverse rules regenerate every cell of the part 1 tables.
- **Device check:** adb can't type Japanese (`2026-10-26-dev-environment.md` §5). Ask the user to try a few conjugated words on the phone.

## Known issues

- **Play Protect:** Google Play Protect's on-device scan classified the debug APK as "HARMFUL". This is typical for sideloaded unsigned apps. The app still runs.
- **History lost when Android kills the app:** the back stack lives in a ViewModel, so it survives configuration changes but not process death. Reopening the app then starts at an empty search.
- **Search speed only partly measured:** search timings are written to the log (`adb logcat -s Search:I`). Seen so far: a 100-result English search ("hang") takes 120–400 ms, and short Japanese searches take under 10 ms. One-character prefix searches and the first-launch database copy haven't been timed.
